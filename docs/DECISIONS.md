# Decisions

Notable project decisions, newest last. Each line: date, decision, why.

## 2026-10-03 — Foundation
- **Next.js 16.3 + Tailwind 4.** Tailwind 4 has no `tailwind.config`; design tokens live in `@theme` in `src/app/globals.css`, which also emits them as CSS variables.
- **Script font falls back to STIX Two Text Italic.** Sloop isn't in `/docs/brand/Fonts` (only an SFT Schrifted Serif *trial* font, not licensed for production). `--font-script` points at STIX Italic, the brand guide's stated alternative; swapping in Sloop is one line in `src/app/fonts.ts`.
- **Env split.** One zod schema (`src/lib/env/schema.ts`) checked in `next.config.ts` so dev/build fail loudly; `env` (server-only, secrets) and `publicEnv` (browser) are separate modules so secrets can't reach client bundles.
- **Favicon** is the dark circular elephant mark from the tertiary logo set.
- **`/docs` stays out of git** except our own docs (`DATABASE.md`, `DECISIONS.md`, `OWNER_TODO.md`). The GitHub repo is public; client PDFs, catalogue prices and the trial font must not be published.
- **Git pushes use the `github-mustu124` SSH alias** from `~/.ssh/config`.

## 2026-10-03 — Database
- **Money in paise** (integers) everywhere; formatting only at display.
- **`search_vector` maintained by trigger**, not a generated column: generated columns can't read the category name or use non-immutable `array_to_string`. Accents are stripped (`unaccent`) so "mithu" finds "Mithū".
- **Gap-free numbering** via `document_counters`: order numbers `ERY-2026-00001` per calendar year; GST invoice numbers `ERY/26-27/00001` per financial year, assigned only once paid.
- **Stock is held at order creation**; unpaid Razorpay orders are cancelled and released after 30 minutes by `pg_cron` (`expire_pending_orders`, every 10 minutes).
- **`restore_stock` also reverses gift card balance**, idempotently.
- **Added `contact_messages`** (contact form stored for `/admin`, since no email).
- **Only owners can manage `admin_users`** so staff cannot promote themselves.
- **Customer email is optional; phone is required.**
- **No Cash on Delivery.** `payment_method` is `razorpay` or `gift_card` (an order fully covered by a gift card is placed and paid immediately). COD columns removed.
- **Default shipping ₹100 flat**, no free-shipping threshold (owner's instruction "for now").
- **Migrations 0100–1000 were applied by the owner via the SQL editor**, so Supabase's migration history must be repaired before the first `db push` (command in `docs/DATABASE.md`).
- **Owner admin row** added for the only Auth user, `admin@forever.com`.

- **Routes:** `/shop` (Shop All), `/shop/[slug]` for the five categories and the curated lists (new-arrivals, best-sellers, gifts-for-her), `/shop/style/[style]` (STYLE_PAGES in `src/lib/collection/scopes.ts`; "Jhumkas & Chaandbaalis" is one combined page, `jhumkas-chaandbaalis`). Without them, product photos become tiles after every 8 products on mobile and every 12 on desktop (never after the last product, never two in a row), preferring pieces not on the current page; with only one page of products (most categories) they reuse on-page pieces from the far end of the page. The tile captions the piece's name and links to it.
- **Scroll memory:** `ScrollRestorer` saves `scrollY` per full URL in sessionStorage (on scroll, on link click and on pagehide) and restores it only for back/forward navigations (a `popstate` flag set by `HistoryFlag` in the store layout, or a back_forward page load). Verified with Playwright on Chromium and WebKit at 375 and 1280.
- **Mobile sort** is a native select styled as an outlined "SORT BY" button (the phone's own picker shows the options).
- **Canonical URLs** are the bare collection path (no filters, sort or page). Breadcrumb JSON-LD: Home › Shop › <collection>.
- **Collection pages are partial prerenders:** the title and description are static; the filtered grid streams in the same response.
- **Playwright now runs against a production build** (`next build && next start`) by default: `next dev` under four parallel workers clicked before hydration and threw transient errors. `E2E_DEV=1` uses the dev server.

## 2026-10-03 — Search
- **`search_products(q, p_limit, p_offset)`** (migration `20261003001200`; `limit`/`offset` are SQL keywords, hence the `p_` prefix). Prefix full-text search on the unaccented `search_vector` ranks results (plus name similarity); only when that finds nothing does it fall back to pg_trgm `strict_word_similarity` (threshold 0.4) against name, category, styles and stones. Fuzzy-only-as-fallback keeps "ring" from matching every earring. Security definer with an explicit `is_published` filter. Tested in PGlite against the live catalogue: chandbali, gaja/Gajā, pakhi/Pākhi, kum (prefix), pendnt and necklase all work; short Hindi spellings too far from the catalogue word for trigrams (jumka 0.27, jumki 0.18) are covered by the synonym map.
- **Synonyms** (`src/lib/search/synonyms.ts`) expand each word into OR-alternatives while keeping the word itself (so "moon" matches the Celestial style and "moon-shaped" descriptions): jhumka/jhumki/jumka → jhumkas; chandbali/chaandbali → chaandbaalis; dangler/dangling → danglers, drop → danglers or drops; stud → studs; kundan/jadau → polki; moti → pearl; mop and "mother of pearl" → mother-of-pearl; moon/chand → celestial; elephant/haathi → gaja; lotus → kumud or padma. Accents are stripped and stop words dropped.
- **Fallback until the migration is applied:** if the RPC is missing (PGRST202), search matches name, slug (unaccented, so "gaja" still finds Gajā), short description and styles with ILIKE, ANDing the word groups. No typo tolerance beyond the synonyms. Misses can't be logged until then either.
- **/search** reuses the collection body (filters, sort, chips, 24 per page, scroll memory) scoped to the matching product ids (at most 200, best first). "Curated" is relabelled "Relevance" and orders by rank; no lifestyle tiles; `noindex`. Zero results: "We couldn't find that piece", the quick chips and the Best Sellers carousel, and the term is logged with `after()` (so the response isn't delayed).
- **Header search** is a combobox: quick chips (Studs, Jhumkas, Pearl, Minimal, Polki, Necklace Sets) on focus; after 2 characters a 200ms-debounced dropdown from `/api/search` (cached per query) with up to 6 products, up to 3 category/style/list links and "View all"; arrow keys, Enter and Esc; Enter on the field opens `/search?q=`. It's still a plain GET form without JavaScript, and it keeps text typed before the page finished loading. Added a `polki` style page for the chip.
- **Next 16 keeps the previous page mounted but hidden** (React Activity) for instant back navigation, so tests count only visible cards. The store layout marks `<html data-hydrated>` once interactive; tests wait for it instead of network idle.

## 2026-10-03 — Checkout
- **No coupons, so no coupon field.** The summary has a gift card field only; the brief's "expired coupon" test became an expired gift card. There is no discount line.
- **No owner email on new orders** (the owner removed email earlier). New orders show in /admin and each order's `order_events` timeline records creation, payment attempts and confirmation.
- **`payment_method` stays `razorpay | gift_card`** (default `razorpay`) rather than a check allowing only `razorpay`: a gift card that covers the whole total places the order without Razorpay, and the invoice should say so.
- **Invoice number is the GST series** `ERY/26-27/00001` (consecutive per financial year, only paid orders get one), shown next to the order number `ERY-2026-00001`. The brief asked for "same as order number", but order numbers are taken by unpaid attempts too, which would leave gaps in the GST series. The invoice and the confirmation page show both numbers.
- **Unpaid orders expire after 60 minutes, checked every 30, by pg_cron** (migration 13) rather than Vercel Cron: Vercel's Hobby plan runs cron only once a day, and the database already has the job.
- **Stock is reserved when the order is created** (before payment), so two shoppers can't pay for the last piece. The second sees "Sorry, one of your pieces has just sold out" with a "Remove it" button. A payment that arrives after its order expired takes the stock again if it's still there; otherwise the page tells the customer a refund is coming and the order gets a "REFUND NEEDED" note.
- **One checkout attempt = one idempotency key** (a UUID generated in the browser for the current details and cart). Double clicks and retries after a failed or dismissed payment reuse the same pending order and Razorpay order; changing the cart or details starts a new attempt (the old one expires).
- **Whichever of /verify and the webhook comes first places the order** (`confirm_payment` locks the row; the other becomes a no-op). Both check HMAC-SHA256 signatures with `timingSafeEqual`; the webhook checks the amount too. The browser goes to the confirmation page even if /verify can't be reached, and that page polls every 3 seconds until the webhook confirms.
- **The summary is priced by the database** through a dry run of `create_order` (nothing written), so the shopper sees exactly what they'll pay, including the shipping rule for their pincode and state.
- **Pincode autofill** uses India Post's public API (`api.postalpincode.in`) through `/api/pincode/[pin]`, cached for days. It fills city (district) and state only if the shopper hasn't typed their own. If the lookup fails, they type them.
- **Mobile number** accepts +91, spaces and dashes and stores the 10 digits. **Email is required** (the invoice shows it; the site never emails it).
- **Invoice PDF** (react-pdf) on brand: elephant mark and wordmark as vector paths, "Heirlooms, Reimagined", Montserrat and STIX Two Text bundled in `src/fonts/pdf` (the built-in PDF fonts have no ₹ sign). "Tax Invoice" with GSTIN and an "Includes GST" line only when a GSTIN is set. It is made once after payment (in `after()`, so the response isn't delayed), stored in the private `invoices` bucket, and made on demand if missing. It is never sent to the customer.
- **Confirmation page** `/order/<number>?t=<token>` sits in the store layout (so shopping can continue), is `noindex` with no referrer, and 404s without the right token. It is the only place the bill appears.
- **Razorpay is called with `fetch`**, not the `razorpay` npm package (removed): two calls don't justify the dependency, and `RAZORPAY_API_BASE` lets the tests point it at a fake.

## 2026-10-04 — Analytics (/admin/analytics)
- **No coupons.** The brief's "Coupon and Gift Card Usage" is gift cards only, and the test orders use no coupons: CLAUDE.md rules coupons out and the tables were removed earlier.
- **Definitions.** A sale is an order with `payment_status = 'paid'` whose status isn't cancelled (or still awaiting payment), dated by `paid_at` in India time. Revenue is the sum of `orders.total`, the amount paid online after any gift card; the value paid by gift card is shown beside it. A refunded order has `payment_status = 'refunded'`, so it is not a sale: revenue is already net of refunds, and refunds are listed on their own line (amount and count, by original payment date). A returned order still counts until it is marked refunded.
- **Category and product revenue is item revenue** (price × quantity), before shipping and gift cards, so the category total differs from Total Revenue by shipping and gift cards. Location revenue uses order totals.
- **Everything is computed in Postgres** (migration 16, idempotent, applied with the CLI): `analytics_summary`, `analytics_sales_over_time`, `analytics_by_category`, `analytics_product_sales`, `analytics_low_stock`, `analytics_by_location`, `analytics_gift_cards`, `analytics_repeat_customers`, on a shared `analytics_sales(from, to, include_test)` set. The server only picks dates, merges the previous period for the "% change" figures, and groups product rows into designs.
- **Access.** The functions are executable by `service_role` only (revoked from public, anon and authenticated). The admin pages call them through the service-role client after `requireAdminPage()` / `getAdmin()`. Each function also runs `analytics_guard()`, which refuses a caller that is neither `service_role` nor `is_admin()`. They run as the caller, not as definer. (`is_admin()` alone can't be the check: the server calls with the service role, which has no user id.)
- **Previous period** is the same number of days immediately before the range. "% change" is whole percent, "new" when the previous period had nothing, "—" when both are zero.
- **Sales over time is two small charts, not one chart with two lines.** Revenue (₹) and orders are different scales, and a dual-axis chart invents a relationship between them. The two charts share the date axis and one tooltip (date, revenue, orders). Buckets: by day up to 31 days, by week (Monday start) up to 183, then by month. Each has a table view.
- **Ink only.** One series per chart, in the ink colour on white, as asked. The bundled palette validator flags ink as too dark and too grey for *categorical* palettes; that check is about telling several series apart by colour, which doesn't apply to a single series (contrast passes). Bars are thin, values sit at the bar ends, change figures carry a sign and an arrow as well as colour. Bar charts are plain HTML, and recharts is used only for the two line charts.
- **Best sellers group by design:** the name before " – ", so "Dori Ring – Green" and "Dori Ring – Pink" (separate products in this shop) roll up under "Dori Ring", along with real options; "Show N versions" expands them. Top 20, sortable by units or revenue in the browser.
- **Low stock** uses `site_settings.low_stock_threshold` (default 2, editable on the page by owner or staff), always shows current stock with sales from the last 30 days (it ignores the date picker), and sorts by the soonest to run out: sold out first, then days left (`stock ÷ (units sold in 30 days ÷ 30)`), then "—" where nothing sold. The dashboard's low-stock figures use the same threshold.
- **Repeat customers** are phone numbers reduced to their last 10 digits. Repeat = ordered before the range, or more than once within it. The table shows lifetime orders and spend up to the end of the range. The page masks phones (98XXXXX210) and links each customer to `/admin/orders?customer=<their latest order number>`, so no phone number appears in a link; the orders list resolves that to the phone. Staff can see the section; only the owner can download its CSV, which has full numbers (403 otherwise).
- **CSV downloads** come from `/admin/analytics/export?section=…` with the same range, generated by the same functions; amounts are plain rupee numbers. The locations CSV is at city level. Cells that could be read as formulas are neutralised (`src/lib/admin/csv.ts`, now shared with the orders export).
- **Test orders.** `orders.is_test` and `gift_cards.is_test` (existing E2E gift cards were flagged). Analytics leaves test data out. "Include test orders" appears only in development, or when `ANALYTICS_TEST_TOGGLE=1` is set (the Playwright server sets it, since it tests a production build). `pnpm seed:test-orders` writes 150 deterministic test orders over 90 days (144 sales, 3 refunded, 3 cancelled, 95 customers with a dozen regulars, 14 cities, 4 gift cards) straight into the tables, without touching stock, order numbers or invoice numbers; `pnpm clear:test-orders` removes them.
- **Verified by hand (2026-10-04, last 30 days, test orders included):** separate SQL written without the shared helper gave revenue ₹2,80,750, 46 orders, average ₹6,103.26, and Earrings ₹1,11,250 / Necklace Sets ₹95,550 / Pendants ₹52,050 / Rings ₹21,300, identical to the functions and the page. `pnpm test:db` also checks every function against nine hand-built orders (India-time day boundaries, refunds, cancellations, test flags, phone normalisation). The test orders were removed afterwards.
- **Dashboard:** a "Last 30 days" strip (revenue, orders, average order, low-stock count) links to Analytics.
